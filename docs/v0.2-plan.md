# Encompute 0.2 — Real Private Execution

Status: done, 2026-09-24. `scripts/two-machine-demo.sh` runs the definition of done; CI runs it on every push.

## Goal

A client encrypts a 384-dimensional query and sends only ciphertexts and
evaluation keys to an evaluator on another machine. The evaluator computes
encrypted similarity scores and returns ciphertexts; only the client can
decrypt them. The evaluator never receives the secret key or any plaintext
input or output, and its binary contains no Encompute keygen or decrypt code.

Done when the demo runs on two machines (or a host and a container), the
result matches plaintext within the declared tolerance, and `encompute
explain` reports parameters, operation counts, measured bytes, time,
memory and error.

## Non-goals

TFHE, MPC, TEE, new schemes, GPU, bootstrapping, private RAG, LLMs, SQL,
Kubernetes, multi-user KMS.

## Design decisions

**D1. Two binaries.** `encompute` (client: compile, keys, run, explain,
bench, audit) and `encompute-evaluator` (serve, worker). `encompute serve`
starts `encompute-evaluator`. Only the client binary links the client-side
crypto crate.

**D2. Split crypto crates and shim.**
- `encompute-openfhe` (evaluator side): context from parameters, evaluation
  ops, deserialization of evaluation keys, (de)serialization of ciphertexts.
- `encompute-openfhe-client`: key generation, encryption, decryption,
  serialization of evaluation keys and the secret key.

The C++ shim is split the same way, into two translation units compiled
into the respective crates. Traits in `encompute-backend`: `CkksEvaluator`
and `CkksClient`. The mock implements both.

**What "cannot decrypt" means.** The guarantee is cryptographic: the
evaluator never holds the secret key. Code absence is defense in depth. The
evaluator binary has no Encompute keygen/decrypt entry points (a CI test
checks its symbols), but statically linked OpenFHE still contains
decryption routines internally that cannot be fully stripped.
`encompute audit` reports both facts. Docs say "holds no secret key", never
"cannot run decryption code".

**D3. Envelope.** Every object on the wire or on disk (ciphertexts,
evaluation keys, secret key, results) is an Encompute envelope, never raw
OpenFHE bytes:

```text
magic "ENCM" | format_version u16 | header length u32 | header (JSON) | payload | sha256(all before)
header: kind, scheme, backend, backend_version, artifact_format,
        parameter_set_id, program_id, key_id, payload_len
```

`parameter_set_id` = SHA-256 of `parameters.json`; `program_id` = SHA-256 of
`program.eir`; `key_id` = SHA-256 of the evaluation-key payload. A reader
rejects a wrong kind, version, backend, parameter set, program or key, or a
checksum mismatch, with ENC16xx codes.

**D4. Protocol: HTTP/1.1, JSON control plus binary envelopes.**

| Endpoint | Body | Returns |
|---|---|---|
| `GET /v1/info` | — | protocol version, backend, loaded program IDs |
| `POST /v1/programs` | `program.eir` | `program_id` (the evaluator recompiles it itself) |
| `POST /v1/keys` | evaluation-key envelope | `key_id` |
| `POST /v1/jobs` | input envelope (program_id, key_id) | `job_id` |
| `GET /v1/jobs/{id}` | — | status, timings |
| `GET /v1/jobs/{id}/result` | — | output envelope |

Evaluation keys are uploaded once per key ID and reused. TLS terminates at a
reverse proxy in 0.2; built-in TLS (rustls) is a follow-up. The envelope
checksum detects corruption, but authentication is out of scope.

**D5. Process isolation.** The gateway process owns HTTP and a pool of
`encompute-evaluator worker` processes speaking length-prefixed envelopes over
stdin/stdout. Keys are loaded into each worker. We benchmark 1 worker vs N
workers vs single-process-serialized; the 16-thread OpenFHE mutex stays
inside each process.

**D6. Artifact provenance** (format 2): `compiler_version`, `ir_version`,
`plan_version`, and `crypto { scheme, backend, backend_version,
parameter_profile, parameter_selector_version, security_table }`. Changing
the parameter-selection algorithm bumps `parameter_selector_version`.
Artifacts remain deterministic and key-free.

**D7. Keys on disk.** `encompute keys generate model.encompute` writes
`model.keys/secret.key` (mode 0600, client only) and `model.keys/eval.keys`
(to upload), both enveloped and bound to the parameter set.

## Phases

| Phase | Deliverable | Done when |
|---|---|---|
| P1 hardening | Parameter conformance (check tier: 10k-point grid vs OpenFHE; run tier: encrypted random programs); parser/artifact fuzzing; artifact provenance v2; threat-model wording | scheduled CI runs the full grids; fuzzers find no panics |
| P2 split + serialization | `CkksClient`/`CkksEvaluator`; shim split; envelope crate; ciphertext, key and secret-key serialization | round trips byte-stable; every wrong-X rejection tested |
| P3 network | `encompute-evaluator serve`; `encompute keys generate`; `encompute run --remote` | end-to-end over localhost; malformed-request and interrupted-connection tests |
| P4 workers | worker processes; concurrency benchmark (serialized vs processes) | multi-worker stress test; results in `docs/benchmarks.md` |
| P5 measurement | `explain --measure` (bytes, times, peak RSS, error, ranking consistency); benchmark suite (scalar, dot, matvec, logistic, 384-D); `encompute audit` | numbers measured, reproducible command recorded |
| P6 two-machine demo | container image for the evaluator; scripted demo; CI job running client ↔ container | demo passes in CI |

## Required tests (from the milestone spec)

IR determinism · artifact determinism · artifact corruption · ciphertext
corruption · wrong key · wrong parameters · wrong program · serialization
round trips · network interruption · malformed requests · parameter fuzzing ·
differential correctness (including ranking consistency) · OpenFHE FFI stress
· multiple workers · no secret-key or decrypt symbols in the evaluator.
