# Encompute v0.1 — Build Plan

Status: implemented, 2026-09-24. See *Status* at the end for results and deviations.

## Goal

Prove the architecture end to end on one scheme and one backend:

> A developer writes a typed Python function, Encompute compiles it to a
> backend-independent IR, picks CKKS parameters automatically, runs it
> encrypted on OpenFHE, and proves the encrypted result matches plaintext
> within a declared error.

Anything that does not serve that sentence is out of scope.

## Scope

### In

- Python SDK (distribution `encompute`, see ADR-003): `@encompute.compile`, `secret[...]`, `public[...]`, tracing frontend
- Encompute IR: SSA graph, textual `.eir` form, serde
- Analyses: privacy flow, range (interval), multiplicative depth, precision estimate
- CKKS lowering and automatic parameter selection (128-bit classical)
- Backends: `mock` (always built) and `openfhe` (feature flag)
- Runtime: clear, mock and encrypted modes; differential testing harness
- Compiled artifact: `model.encompute/`
- CLI: `compile`, `run`, `test`, `explain`, `bench`

### Out (with target version)

| Deferred | Target |
|---|---|
| Automatic packing / rotation optimization | 0.2 |
| Bootstrapping | 0.2 |
| GPU execution | 0.2 |
| Networked client/server, stable ciphertext envelope | 0.2 |
| Integers, exact comparison, division, lookup tables (TFHE-rs) | 0.3 |
| Scheme planner, hybrid execution, HEIR / Lattigo backends | 0.3 |
| KMS, cloud, auth, audit logs, cost estimation, `audit` command | 0.4 |
| MPC, TEE, SQL, ONNX/PyTorch import, LLMs | later |

## Supported programs in v0.1

Types:

- `secret[float, lo:hi]`: encrypted scalar with declared range
- `secret[Tensor[n], lo:hi]`: encrypted vector, `n <= N/2` slots
- `public[float]`, `public[Tensor[n]]`: plaintext constants and weights

Operations: `+`, `-`, `*` (ciphertext–ciphertext and ciphertext–plaintext),
negation, `sum`, `dot`, `matvec` (diagonal method), `poly(x, coeffs)`, and
built-in approximations `encompute.sigmoid` and `encompute.square` over the declared range.

Rejected at compile time, with a stable error code and an explanation:

| Code | Cause |
|---|---|
| ENC1001 | Python control flow on a secret (`if secret:`, `while`, `bool()`) — suggest `encompute.select` (0.3) |
| ENC1002 | Division by a secret value |
| ENC1003 | Comparison of secrets (`<`, `>`, `==`) — needs TFHE (0.3) or `encompute.approx.sign` (later) |
| ENC1004 | Secret flows into a public sink (`print`, `str`, `format`, logging, return as public) |
| ENC1101 | Input range not declared |
| ENC1201 | Depth exceeds the largest 128-bit parameter set without bootstrapping |
| ENC1202 | Requested precision unreachable at the computed depth |

**Why these limits.** CKKS is approximate arithmetic. Exact comparison and
division are not native operations, and pretending otherwise produces silently
wrong results. v0.1 rejects them explicitly. The spec's `credit_score` example
(integer division plus comparisons) is a v0.3 target. The v0.1 flagship demo is
CKKS-native (see *Demos*).

Input ranges must be declared. Range *propagation* is inferred, but ranges
on inputs cannot be inferred from code alone.

## Crates

Rust workspace, eight crates. Arrows are dependencies.

```text
encompute-py ──┐
encompute-cli ─┴─► encompute-runtime ─► encompute-backend ◄── encompute-openfhe
                   │               ▲
                   ▼               │
               encompute-ckks ──────────┘
                   │
                   ▼
             encompute-analysis ─► encompute-ir
```

| Crate | Responsibility | Key types |
|---|---|---|
| `encompute-ir` | SSA graph, types with visibility + range metadata, builder, verifier, `.eir` printer/parser, serde | `Program`, `Value`, `Op`, `Type`, `Visibility` |
| `encompute-analysis` | Privacy-flow check, interval range propagation, multiplicative depth, precision estimate. Pure functions over `Program`. | `PrivacyReport`, `RangeMap`, `DepthMap`, `PrecisionEstimate` |
| `encompute-ckks` | Lower Encompute IR to a CKKS plan (encode, mul, rescale, relinearize, rotate, level management). Parameter selection against a pinned security table. | `CkksPlan`, `CkksParams`, `SecurityTable` |
| `encompute-backend` | `CkksBackend` trait over plan ops; `MockBackend` in the same crate | `CkksBackend`, `MockBackend`, key role types |
| `encompute-openfhe` | OpenFHE CKKS through a `cxx` bridge; behind the `openfhe` feature | `OpenFheBackend` |
| `encompute-runtime` | Execute a plan on a backend; clear-mode interpreter; differential harness; artifact read/write | `Executor`, `DiffReport`, `Artifact` |
| `encompute-cli` | `encompute compile / run / test / explain / bench` | — |
| `encompute-py` | PyO3 bindings + Python package (`maturin`) | `encompute.compile`, `encompute.secret`, `encompute.Client` |

Rules:

- `encompute-ir` and `encompute-analysis` know nothing about CKKS or OpenFHE.
- Only `encompute-openfhe` links C++.
- In v0.1 the backend trait is CKKS-shaped on purpose. It becomes
  scheme-generic in v0.3, when a second scheme exists to generalize from.
  Designing it earlier means guessing.

## Key design decisions

**D1. Tracing frontend.** Calling a `@encompute.compile` function with proxy
objects records IR. `Proxy.__bool__`, `__str__`, `__format__` and
`__index__` raise ENC1001/ENC1004. That gives the privacy-flow checks in
Python for free. The Rust verifier re-checks the IR anyway.

**D2. Two IR levels.** Encompute IR is tensor-level and scheme-free. `CkksPlan`
is the low-level op list (rotations, rescales, levels). The plan is a
separate type, not an IR dialect.

**D3. Parameter selection with provenance.** Inputs: depth, declared ranges,
precision target, slot count. Outputs: ring dimension N, modulus chain, scale
bits. Max log Q per N comes from a pinned table: HE Standard 128-bit classical,
cross-checked against OpenFHE's `HEStd_128_classic`. `parameters.json` records
the table source and version. The OpenFHE backend re-validates the parameters
at context creation, and a mismatch is a hard error.

**D4. Precision: estimate, then measure.** `encompute-analysis` gives an analytic
estimate for `explain`. Correctness is decided by `encompute test`, which measures
max error over random inputs from the declared ranges and fails if it exceeds
the target. The estimate is advisory; the measurement is the gate.

**D5. Mock backend simulates CKKS bookkeeping.** It tracks level and scale
exactly like the real plan, and adds Gaussian noise with a configurable sigma.
Level and scale bugs show up without OpenFHE, and CI runs everywhere.

**D6. Key roles separated now, co-located for now.** The API splits `Client`
(secret key: keygen, encrypt, decrypt) from `Evaluator` (evaluation keys
only). v0.1 runs both in one process. v0.2 puts a network between them
without an API break.

**D7. Threat model v0.1.** Trusted client; honest-but-curious evaluator;
decrypted results are never returned to the evaluator. The last condition is
there because of CKKS IND-CPA-D (Li–Micciancio 2021). Written into
`security.json` and `docs/threat-model.md`.

**D8. No bootstrapping.** Circuits must fit the depth budget of the largest
128-bit parameter set (N = 2^16). Otherwise the compiler rejects them with
ENC1201.

## Compiled artifact

```text
model.encompute/
├── program.eir       Encompute IR, textual
├── plan.json          CKKS plan
├── parameters.json    N, moduli, scale, security table + version
├── security.json      threat model, visibility of inputs/outputs, eval keys required
└── manifest.json      sha256 of every file above, encompute version, backend version
```

Keys are never written into the artifact. Compiling the same source twice
with the same Encompute version must give byte-identical artifacts; a CI test
enforces this.

## Differential testing

`encompute test model.encompute --cases 1000 --seed 42`

1. Sample inputs uniformly from the declared ranges, plus range endpoints.
2. Run clear (f64 interpreter), mock, and encrypted.
3. Report max and mean absolute error per output; compare with the target.
4. Exit non-zero on any failure, and print the failing seed and inputs.

The same harness backs the Rust test suite (`proptest`) and the Python tests
(`hypothesis`).

## Demos (exit criteria)

1. **Encrypted logistic-regression scoring.** 32 features:
   `sigmoid(dot(w, x) + b)`, sigmoid as a degree-7 polynomial over the declared
   range.
2. **Encrypted embedding similarity.** 384-dimensional query against 64
   public normalized document embeddings (`matvec`), returning encrypted scores.

v0.1 ships when, on a laptop CPU:

- both demos run end to end from `pip install` (from source) in under ten
  minutes for a new developer;
- `encompute test` passes 1000 cases, max error ≤ 1e-3 on demo 1;
- `encompute explain` prints depth, levels, rotations, parameters and the estimated
  vs measured error;
- `encompute bench` reports keygen / encrypt / eval / decrypt time and ciphertext
  sizes;
- artifacts are reproducible; CI is green with `mock` and with `openfhe`.

## Status

All milestones are implemented. M2 (Python frontend) was built after M5, so
it could sit directly on a working compiler and runtime.

Deviations from the plan above:

- **Precision estimate** lives in `encompute-ckks`, not `encompute-analysis`: it depends
  on the lowering (approximation degrees, scale). Depth is also computed on the
  lowered plan.
- **Sigmoid degree** is chosen per program, not fixed at 7: the lowest
  Chebyshev degree whose error on the analyzed range is within half the
  precision budget (demo 1: degree 16 over [-6.27, 6.77], error 4.2e-4).
- **matvec** uses hybrid diagonals (one per padded row) with baby-step /
  giant-step rotations and a fold, not the square diagonal method: 64
  plaintext multiplications instead of ~512 for the 64 × 384 demo.
- **OpenFHE** is linked statically. Every OpenFHE call is serialized by one
  mutex, because v1.5.1 corrupts results under concurrent use (ADR-001).
- **Public values** are compile-time constants. Runtime public inputs are not
  in v0.1.
- **`encompute compile model.py`** delegates to `python -m encompute compile`, since
  tracing needs the Python SDK.
